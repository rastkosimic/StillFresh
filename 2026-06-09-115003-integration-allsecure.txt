  ---
  AllSecure Integration Overview for StillFresh

  What Changes vs. What Stays

  The payment-service keeps its entire internal architecture: entities, Kafka
  topics, ledger, payout scheduler, SEPA-XML executor, and MoR flow all remain
  untouched. Only the Stripe SDK calls get replaced. AllSecure has no Connect
  equivalent, so vendor onboarding becomes MoR-only for all vendors (the
  StripeConnectController + StripeConnectService are removed).

  ---
  Card Registration Flow

  Current (Stripe): Frontend sends a Stripe card token → backend calls
  Customer.create() then paymentMethod.attach() → stores stripeCustomerId in
  PaymentUser.

  AllSecure equivalent:

  Frontend (payment.js)
    └─ tokenizes card in iFrame → sends token to backend

  POST /payment/register-card
    └─ PaymentService.registerCard()
         └─ AllSecure API: POST /api/v3  { type: "register", transactionToken:
  "<token>", ... }
              └─ Response: { uuid: "<referenceUuid>", ... }
                   └─ Store referenceUuid + card metadata (last4, expiry, brand)
                        in new CustomerPaymentMethod entity

  Because AllSecure doesn't expose a "list stored cards" API, card metadata
  (last4, expiry, brand, isDefault flag) must be persisted locally at
  registration time. The existing PaymentUser loses stripeCustomerId; a new
  CustomerPaymentMethod table holds one row per stored card with its
  referenceUuid.

  transactionIndicator: SINGLE on first register. Subsequent charges use the
  stored UUID.

  ---
  Card Management Flow

  ┌──────────┬──────────────────────────────┬──────────────────────────────┐
  │  Action  │      AllSecure API call      │           Local DB           │
  ├──────────┼──────────────────────────────┼──────────────────────────────┤
  │ List     │ No API call needed           │ Query CustomerPaymentMethod  │
  │ cards    │                              │ by userId                    │
  ├──────────┼──────────────────────────────┼──────────────────────────────┤

  ├──────────┼──────────────────────────────┼──────────────────────────────┤

  │ card     │  + referenceUuid             │                              │

  │ Set      │ No API call                  │ Toggle isDefault flag        │
  │ default  │                              │                              │
  └──────────┴──────────────────────────────┴──────────────────────────────┘

  This is simpler than Stripe — card metadata is owned locally, AllSecure only
  holds the vault reference.

  ---
  Order & Payment Flow

  Current (Stripe): PaymentRequestEvent consumed → PaymentIntent.create() with
  CaptureMethod.MANUAL + TransferData (Stripe Connect routing) →
  PaymentSuccessEvent published → later capture() on fulfillment.

  AllSecure equivalent — two-phase (Preauthorize → Capture):

  Kafka: PaymentRequestEvent consumed
    └─ PaymentService.processPaymentRequest()
         └─ AllSecure API: POST /api/v3
              {
                type: "preauthorize",
                referenceUuid: <customer's stored card UUID>,
                transactionIndicator: "CARDONFILE",
                amount: <gross amount>,
                currency: "RSD",
                merchantTransactionId: <unique per order>,
                callbackUrl: "https://.../payment/allsecure/callback",
                successUrl, errorUrl, cancelUrl
              }
         └─ Response: { returnType: "PENDING", uuid: <paymentIntentId
  equivalent> }
              └─ Store AllSecure UUID in PaymentTransaction.paymentIntentId
              └─ Await async postback to /payment/allsecure/callback

  POST /payment/allsecure/callback  (new endpoint)
    └─ Verify X-Signature (HMAC-SHA512)
    └─ If status == "OK"  → publishPaymentSuccessEvent()
    └─ If status == "ERROR" → publishPaymentFailureEvent()

  Capture (on order pickup confirmation):
    Kafka: PaymentCaptureRequestEvent consumed
      └─ AllSecure API: POST /api/v3
           { type: "capture", referenceUuid: <preauthorize UUID> }
      └─ publishPaymentCapturedEvent()

  Cancel (on order expiry/cancellation):
    Kafka: PaymentCancelRequestEvent consumed
      └─ AllSecure API: POST /api/v3
           { type: "void", referenceUuid: <preauthorize UUID> }

  DinaCard goes through the identical flow — it's just a card scheme. The only
  difference is currency: "RSD" and the customer having registered a DinaCard
  rather than Visa/Mastercard.

  3DS is handled transparently: if AllSecure returns returnType: "REDIRECT" (3DS
   challenge), the response includes a redirect URL that the frontend must
  follow. The callback then fires on completion.

  This path is already implemented and production-ready. The

  ---
  You were right to push back. I was too hasty. Here's what AllSecure actually
  has:

  IBAN storage does exist — CustomerProfile supports a PaymentInstrument with
  METHOD_IBAN, backed by IbanData (IBAN, BIC, mandateId, mandateDate). You can
  store a bank account reference and retrieve it by profile ID later.

  However — important caveat: the IbanData model carries mandateId and
  mandateDate fields. Those are SEPA DirectDebit mandate fields — meaning this
  IBAN storage is designed for pulling money from a customer's bank account
  (e.g. customer pays by bank debit), not for pushing money out to a vendor.

  For outbound vendor payouts, AllSecure has two mechanisms:

  1. Payout transaction — sends money to a bank account. The IBAN is passed
  directly in the request (via the Customer/IbanCustomer fields), not
  pre-registered. So you can pay to an IBAN per-transaction without needing to
  store it in AllSecure first.
  2. TransactionSplit — the more Stripe-Connect-like feature. A single customer
  charge is split between the platform and one or more
  sellerMerchantGuid-identified sub-merchants. The vendor must be registered
  with AllSecure as a sub-merchant first and gets a sellerMerchantGuid. This
  allows split routing at charge time, similar to Stripe's transfer_data.

  Bottom line: AllSecure is not as self-service as Stripe Connect (no Express
  account onboarding flow, no vendor dashboard), but it does support:
  - Storing IBANs in CustomerProfile (primarily DirectDebit-oriented)
  - Direct IBAN payouts via the Payout transaction type
  - Marketplace payment splits to registered sub-merchants via TransactionSplit

  For StillFresh vendors, the realistic path would be Payout transactions with 
  IBAN per request (keeping vendor IBANs in StillFresh's own DB), or — if
  AllSecure's Serbian team supports it — registering vendors as sub-merchants
  for TransactionSplit. I'd recommend confirming the TransactionSplit
  availability with AllSecure Serbia directly, as it's connector-dependent.

  Sorry for the overconfident initial claim — the capability is there, just
  structured differently from Stripe.

  ---
  Payment Flow at Pickup — And The 3DS Catch

  What happens when the customer taps "confirm pickup"

  The current Stripe flow maps cleanly to AllSecure:

  Customer taps "confirm pickup" in the app
    └─ PUT /orders/{id}/confirm-pickup  (order-service)
         └─ Publish PaymentCaptureRequestEvent  →  Kafka
              └─ payment-service receives it
                   └─ AllSecure API: POST /api/v3  { type: "capture",
  referenceUuid: <preauth UUID> }
                        └─ Publish PaymentCapturedEvent  →  Kafka
                             └─ order-service: order.status = COMPLETED

  The capture itself is fully automatic, server-to-server, zero customer 
  interaction. No card data is touched again — AllSecure just settles the
  already-held funds. This part works exactly as you'd want.

  ---
  Is it fully automatic after card registration?

  Not quite — and this is where 3DS bites you.

  The authorization (Preauthorize) happens at order placement, not at pickup.
  That's where 3DS can interrupt the flow.

  Customer places order  →  payment-service sends Preauthorize with
  referenceUuid
                                 │
                      ┌──────────┴───────────────┐
                      │                          │
                Frictionless                Challenge required
                (issuer approves              (issuer wants
                 risk silently)               customer to authenticate)
                      │                          │
            returnType: FINISHED          returnType: REDIRECT
            ──────────────────            ──────────────────────
            PaymentSuccessEvent           App must open 3DS page
            Order confirmed.              Customer must tap approve
            Zero friction. ✓             in their banking app / enter OTP
                                          └─ THEN callback fires
                                          └─ PaymentSuccessEvent

  So: the Preauthorize may or may not require customer interaction, depending on
   the issuer's risk decision.

  ---
  The 3DS catch — explained properly

  Frictionless vs. Challenge is decided by the card issuer, not by you.
  AllSecure submits risk signals to the issuer, who either approves silently
  (frictionless) or asks the customer to authenticate (challenge). You cannot
  force frictionless — you can only improve your odds by sending richer data.

  What helps get frictionless:
  - Customer IP address
  - Billing address on file
  - Email
  - Browser/device fingerprint data (3DS 2.x browser data fields)
  - History: how long the card has been registered, number of previous
  successful orders

  The 90-day re-authentication rule — this is the second catch. Even if the
  first order was frictionless, issuers (following Visa/Mastercard 3DS 2.x
  rules, and PSD2 in aligned markets) require a fresh strong authentication at
  least every 90 days for stored-card recurring/on-file charges. After 90 days,
  the next order will force a challenge regardless of risk score.

  Serbia context: Serbia is not in the EU so PSD2 does not apply directly, but
  Visa and Mastercard enforce their own 3DS mandates globally. Serbian issuing
  banks implement 3DS 2.x. So the challenge risk is real — just not as rigidly
  enforced as in the EEA.

  ---
  What this means for the app

  ┌───────────────────────┬─────────────────────────────────────────────────┐
  │       Scenario        │               Customer experience               │
  ├───────────────────────┼─────────────────────────────────────────────────┤
  │ First order,          │ Place order → CONFIRMED. Zero friction.         │
  │ frictionless          │                                                 │
  ├───────────────────────┼─────────────────────────────────────────────────┤
  │ First order, 3DS      │ Place order → app must open 3DS redirect        │
  │ challenge             │ (WebView / browser) → customer approves in      │
  │                       │ banking app or enters OTP → CONFIRMED           │
  ├───────────────────────┼─────────────────────────────────────────────────┤
  │ Repeat order within   │ Same as first frictionless case                 │
  │ 90 days, frictionless │                                                 │
  ├───────────────────────┼─────────────────────────────────────────────────┤
  │ Repeat order, 90-day  │ Same as 3DS challenge case                      │
  │ re-auth triggered     │                                                 │
  ├───────────────────────┼─────────────────────────────────────────────────┤
  │ Capture at pickup     │ Always silent. No 3DS, no customer interaction. │
  └───────────────────────┴─────────────────────────────────────────────────┘

  The key design implication: the order placement screen must handle returnType:
   REDIRECT gracefully — open the 3DS URL in an in-app browser/WebView, wait for
   AllSecure's callback, then show the confirmation screen. If you treat every
  Preauthorize response as immediately final, 3DS challenge orders will silently
   fail.

  Set extraData["3dsecure"]: "OPTIONAL" (not MANDATORY, not OFF) — this lets
  low-risk transactions go frictionless while still falling back to challenge
  when the issuer demands it. OFF removes the liability shift (your platform
  eats fraud chargebacks); MANDATORY will decline DinaCard transactions if the
  issuer doesn't support 3DS enrollment.
