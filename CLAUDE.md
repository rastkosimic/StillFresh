## Build & Test Commands

```bash
# Build all modules from root
mvn clean install

# Build without tests
mvn clean install -DskipTests

# Build a single service
cd <service-name> && mvn clean install

# Run all tests for a service
cd <service-name> && mvn test

# Run a specific test class
cd <service-name> && mvn test -Dtest=ClassName

# Run the full system
docker-compose up -d

# Rebuild and restart a single service
docker-compose up -d --build <service-name>
```

## Architecture Overview

StillFresh is a **food waste marketplace** where vendors sell discounted surplus food to customers. It is an event-driven microservices platform built with Spring Boot 3.3.2 / Java 17 / Spring Cloud 2023.0.3.

### Services and Ports

| Service | Port | Role |
|---|---|---|
| `api-gateway` | 8080 | Single entry point; routes via Eureka discovery |
| `authorization-service` | 8082 | JWT auth, OAuth2/Google, token blacklist, password reset |
| `user-service` | 8081 | Customer profiles, favorites, preferences |
| `vendor-service` | 8083 | Vendor onboarding, ratings, payout model management |
| `offer-service` | 8084 | Marketplace listings, geo-search, categories, Redis cache |
| `order-service` | 8085 | Order lifecycle, expiry scheduler, pickup reminders |
| `payment-service` | 8086 | Stripe payments, Stripe Connect for vendors, MoR payouts |
| `notification-service` | 8087 | Firebase FCM push notifications, notification preferences |
| `eureka-server` | 8761 | Service discovery (all services register here) |

Infrastructure: Kafka (KRaft, port 9092), Redis (6379), one PostgreSQL per service (5432–5438).

### Shared Module

`shared-entities/` is a library consumed by all services. It contains:
- **Kafka event classes** under `offer/events/`, `order/events/`, `payment/events/`, `user/events/`, `vendor/events/`
- **Enums**: `Role`, `OfferCategory`, `NotificationType`, `PayoutModel`, `PaymentProvider`, `OnboardingStatus`, `PickupDaySlot`, `PickupMealSlot`
- **DTOs**: `OfferDto`, `VendorStatsResponse`, `OfferSalesBreakdown`, `ErrorResponse`
- **Feign client interfaces** in `client/`

When adding a new inter-service event or shared enum, add it here first and rebuild `shared-entities` before the consuming service.

### Inter-Service Communication

**Asynchronous (Kafka):** The primary pattern. Publishers use `KafkaTemplate`, consumers use `@KafkaListener`. Topic names are defined in each service's `application.yml` and injected via `@Value`. Key flows:
- `OrderPlacedEvent` → Notification Service (push) + Payment Service (charge)
- `PaymentSuccessEvent` / `PaymentCapturedEvent` → Order Service (status update)
- `OfferCreationEvent` / `OfferInvalidationEvent` → consumed by listeners to update caches/state
- `BankingModelChangedEvent` → Notification Service (vendor alert)
- `PasswordUpdateEvent` → User/Vendor services sync auth changes

**Synchronous (Feign):** Used when an immediate response is required (e.g., token validation, fetching offer details for an order). Feign clients are in `shared-entities/client/` or within individual service `client/` packages. Service names are resolved via Eureka.

### Security Model

- All requests enter through the API Gateway, which strips/adds trust headers (`X-Gateway-Secret`).
- Services validate the `X-Gateway-Secret` header via `GatewayTrustFilter` — requests not from the gateway are rejected.
- JWTs are generated by `authorization-service` and optionally validated at the gateway (`gateway.jwt.local-validation-enabled`). Most services trust headers forwarded by the gateway (user ID, role) rather than re-validating the JWT themselves.
- Token blacklisting is done in Redis on logout.
- Google OAuth2 login is handled in `authorization-service` via `OAuth2Controller` / `OAuth2Service`.

### Caching (Redis)

- `offer-service`: caches offer listings
- `authorization-service`: caches tokens and user lookups
- `user-service`: caches user profiles
- Standard Spring `@Cacheable` / `@CacheEvict` annotations; cache type set to `redis` in `application.yml`.

### Database

Each service owns its own PostgreSQL database (database-per-service pattern). Schema is managed via `spring.jpa.hibernate.ddl-auto: update` in development; one-off SQL migration files (e.g., `add_category_column.sql`) are present in service root directories and must be run manually.

### Vendor Payout Models

Vendors can choose between:
- **Stripe Connect** (`PayoutModel.STRIPE_CONNECT`): automated payouts via Stripe
- **Manual / MoR** (`PayoutModel.MANUAL`): ledger-based payouts via `payment-service`

**B2B vendor payouts (MoR / AllSecure):** The ledger pipeline in `payment-service` (`payout_batches` / `vendor_payout_items`) is the single automated path. Rails are swappable via `payout.rail` (`stub`, `sepa-xml`, `cmiplus`). Production target is **Raiffeisen CMIplus** (pain.001 / pain.002 / CAMT). See [`CMIPLUS_PAYOUT_INTEGRATION.md`](CMIPLUS_PAYOUT_INTEGRATION.md).

- Daily scheduler gathers unsettled `ledger_entries` credits → auto-approve → submit to rail
- Admin controls: `/ledger/payouts/*` (pause, hold, cancel, manual execute)
- Stripe Connect vendors are excluded from ledger batches
- Legacy MoR manual `requestManualPayout()` is deprecated

The `payment-service` and `vendor-service` still exchange `VendorPaymentInfoRequestEvent` / `VendorPaymentInfoResponseEvent` for bank detail snapshots. Legacy MoR admin Kafka endpoints remain for historical records.
